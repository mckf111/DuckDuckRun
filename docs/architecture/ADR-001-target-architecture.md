# ADR-001：以“保留并修复”作为 DuckDuckRun 目标架构

| 字段 | 决定 |
|---|---|
| 状态 | **已接受（审查阶段）** |
| 日期 | 2026-08-31 |
| 决策 | **保留并修复**；不局部重构核心渲染/玩法，更不重建 |
| 适用范围 | 后续硬化阶段；本阶段只记录决定，不改代码或部署 |
| 决策负责人 | 项目维护者；审查作者为 Manus AI |

## 背景

DuckDuckRun 是原生 JavaScript Canvas H5：入口、输入、规则、游戏状态、渲染、音频、存档、分享和文化配置均已形成清晰文件边界 [1]。实测桌面、横屏 DPR 2 和竖屏拦截的核心路径能够完成；教程、失败、重开、暂停和失焦暂停均可达 [2]。因此不存在“运行时基础不可用”或“全部体验必须推倒”的结构性证据。

现有 P1 集中在质量与交付边界：`test:browser` 的照片预取断言失败，导致 CI 预览 job 无法通过；已上线 GitHub Pages 又停在旧提交，造成公开版本与当前基线不同 [3] [4]。这些问题具有明确隔离点，分别落在预取契约/浏览器测试与工作流/制品发布，不要求替换 Canvas、状态机、规则模型或视觉资产体系。

## 决策

后续阶段采用**最小风险硬化架构**。保留原生 ESM、Canvas 2D、现有纯函数规则测试、关卡配置、localStorage 存档和 Web Audio。将修复顺序固定为“质量门禁 → 可追溯制品 → 真机验收 → 可访问性/性能/随机可重放”，禁止以更换框架或依赖升级替代问题定位。

| 层 | 现状 | 目标收敛 | 本阶段是否允许修改 |
|---|---|---|---|
| 静态宿主 | `index.html` + Canvas + 原生 ESM | 保留；补充可访问性与版本可见性时遵循渐进增强 | 否 |
| 输入/生命周期 | `src/input.js`、`src/main.js` | 保留单一输入语义；新增可测的暂停、旋转、WebView验收 | 否 |
| 玩法/规则 | `src/game.js`、`src/rules.js` | 保留状态机和规则纯函数；为随机局增加 seed/回放元数据 | 否 |
| 渲染/资产 | Canvas 2D、WebP/JPEG、woff2 | 保留；先真机归因，再做质量等级和资产预算优化 | 否 |
| 音频 | Web Audio 合成 | 保留懒初始化/暂停路径；补 iOS/微信实机回归 | 否 |
| 测试/交付 | Node 测试 + Playwright + Pages workflow | 先使产品契约与测试一致；再用单一制品源、版本/缓存策略发布 | 否 |
| 许可与文化 | CREDITS + 游戏内授权页 | 维持玩家可见署名；补不可变素材台账 | 否 |

## 备选方案与否决理由

| 方案 | 判断 | 否决/采纳理由 |
|---|---|---|
| **保留并修复** | **采纳** | P1/P2 可在现有边界内隔离；核心路径已可运行；修复收益直接对应发布可信度。 |
| 局部重构（替换状态机或 Canvas） | 暂不采纳 | 目前没有状态机无法测试、渲染无法降级或内容模型无法扩展的证据。先修交付和验收，避免把可控问题扩大成迁移风险。 |
| 提出重建（新框架/新引擎） | 否决 | 会重新引入输入、音频、存档、授权页、十关内容与移动适配回归；并不能自动修复 CI/线上漂移。 |

## 成本、风险与回滚

| 路径 | 预估工作量 | 主要风险 | 回滚策略 |
|---|---:|---|---|
| 最小硬化（建议） | 11–19 人日 | 测试契约判定错误；真机性能暴露额外瓶颈；发布流程变更出错 | 每项独立小提交；保留当前静态制品；以版本目录/制品清单支持即时回退。 |
| 局部重构核心层 | 20–30 人日 | 状态/输入/存档回归；视觉重绘；新框架锁定 | 在功能标记后切换；保留现有 Canvas 路径作为长期 fallback。 |
| 等效功能重建 | 30–45 人日 | 内容漏迁、文化/许可重审、全设备回归、上线延期 | 双轨运行；未达到验收矩阵前不替换线上版本。 |

最小硬化占重建成本的约 25%–63%。按照项目约束，只有在下一阶段证明局部修复**稳定超过约 18 人日（约重建下限的 60%）**，或者发现不能与现有运行时隔离的结构性故障，才重新打开“提出重建”的讨论。此阈值不是自动重建按钮，而是要求重新做成本与风险审查的触发器。

## 后果

该决策将阶段 2 的重点锁定在关闭 A-01/A-02、补齐 A-03 至 A-09 的验收基础，而不是扩张内容。它降低短期技术炫技空间，却能最快恢复“仓库、CI、线上版本、设备事实一致”的能力。若这一能力未建立，继续打磨新关卡只会使错误版本更难追踪。

## 回滚与变更控制

后续每一项代码或工作流修改必须具备：明确问题编号、复现命令、通过/失败前后日志、默认分支之外的工作分支、无损回滚提交以及线上制品 SHA/版本标识。本 ADR 不授权发布；发布仅能在 A-01、A-02 和适用设备矩阵门槛关闭后，由独立变更批准。
